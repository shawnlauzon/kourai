It is not a manual step and not `CHECK FAILED:`: the card stays in MERGING, `board-wait.sh` raises `VERIFY:` for that head and the board watcher starts the workflow verifier; its `VERIFIED:` at that head makes the card ready again. Go on with the next card. Any other gate deny is the next item.
- **The merge gate finds a screenshot in git:** the deny reason contains `merge-gate: SCREENSHOTS IN GIT:` (the PR adds or changes a file under `docs/ui_tests/`; screenshots are card attachments only, rules.md, **Screenshots**). It is not a manual step: post `CHECK FAILED: <repo>#<n>: screenshots in git: <the files>` on the card (the card manager sends the Opus feature tester to remove them and the PR goes through the checks again) and go on with the next card. A deny containing `merge-gate: CANNOT LIST FILES:` is the next item.
- **The merge gate finds no card for the PR:** the deny reason contains `merge-gate: NO PR CARD (read back to <date>):` (the gate reads the board's comments of the last 14 days, and further back only while it finds no card, up to 35 seconds; a `PR:` line older than that is not found). Post a fresh `PR: <the PR's url>` on the card you are merging (the same line again; the comment table lists you as a writer of it for this case), wait a few seconds and run the same merge command once more. A second `NO PR CARD` is the manual step below.
- **The merge gate or the `MERGED:` gate runs out of time or breaks:** the deny reason contains `merge-gate: TIMED OUT:`, `merge-gate: TRANSIENT:`, `merged-comment-gate: TIMED OUT:` or `merged-comment-gate: TRANSIENT:` (a Trello read was slow or failed twice; rules.md, **A transient failure**, item 5). Send the main session `SHOW RETRY: <the merge or the MERGED: comment of <repo>#<n> [<card name and link>]>: <the deny reason>; retrying once; nothing to do yet`, wait 10 seconds, check whether the PR is already merged, and run the same command (or post the same `MERGED:` comment) once more. A second one is the manual step below. `merge-gate: CRASHED:` or `merged-comment-gate: CRASHED:` (on stderr, exit 2: the hook itself broke) is the manual step at once. These apply to the `MERGED:` comment only; a card move after a merge is never denied by the gate (it gets no decision when anything fails, and normal permission handling applies).
- **GitHub answers with HTTP 5xx, 429 or a network error** (not a gate denial, not "head moved", not a permission denial): a transient failure (rules.md, **A transient failure**). `SendMessage` the main session `SHOW RETRY: merge of <repo>#<n> [<card name and link>]: <the error>; retrying once; nothing to do yet`, wait 10 seconds, check whether the PR is already merged (`gh pr view`: a merge that went through answers MERGED) and, if not, run the same merge command once more (`--match-head-commit` keeps it safe). A second failure is the manual step below.
- **The merge gate or the permission system denies it** (any other reason), or GitHub refuses for another reason: quote it verbatim on the card. It is a manual step (rules.md, **A manual step**): `WAITS FOR: you: <the step>. Check: <a read that passes once done>` (the script puts Blocked on); report it. The merges already done stay recorded.

### 3. Move the card on

After its last `MERGED:`, the move (a `CARD: AGENTS` card to DONE; any other to MERGED, the top for a 🚨 card, else the bottom).

**Its included cards go with it.** Find the cards whose `INCLUDED IN: <owner/repo>#<n>` names a PR you just merged (`trelloSearch` `search_cards` with `limit` 10 for `"INCLUDED IN: <owner/repo>#<n>"`, then confirm on each). On each, `MERGED WITH: <this card's name and link>: <owner/repo>#<n> @ <its mergeCommit>`, and move it to the list this card went to (bottom).

## While a suite runs

A full API suite takes 9 to 25 minutes. A card with a server PR does not hold up the cards that need no suite. **The loop, for the UNIT wait of step 4 and this suite wait alike:** read MERGING (capped), merge what is ready, make one wait call, read MERGING again after each `RUNNING`, until the run ends (on 2026-10-19 a merger went from `API suite started:` straight to three `ci-wait.sh` calls and left ready `[AGENTS]` cards idle for the whole suite):
- **Go on** with the next cards in MERGING that have **no PR in <server-repo>** (`[AGENTS]` and docs cards, app cards and tests-only cards whose PRs are all in <app-repo>): first a ready 🚨 card with no server PR (read MERGING again, then the topmost ready 🚨 card first), then ready `[AGENTS]` and docs cards, then the others. Check and merge them as in steps 1 to 3, in the same order rule, each from a fresh read of MERGING. A non-🚨 server card is not started while a ready, unstarted 🚨 server card waits. Their merges go into mobile `main`, not `development`, so they change nothing the running suite tests.
- **Between those cards**, look at the run with the plain read `gh run list --repo <server-repo> --workflow integration.yml --limit 10 --json databaseId,status,conclusion` (no wait; find the run by its id). Once it says `completed`, take the suite card at once: `ci-wait.sh run … <id>` for the verdict, then its result. `RUN: STUCK <step>. Tried: <tried>` (exit 6): comment `WAITS FOR: you: <step>. Tried: <tried>. Auto-check: run <repo> <id>` on the suite card and leave it.
- **Back on a suite card that also has a <app-repo> PR**, before step 2: read each unmerged PR's `headRefOid` again and run `pr-conflicts.sh` on the <app-repo> PR again (the cards merged meanwhile may have changed `main`). If a head moved, leave the card for the next run with a comment. If the <app-repo> PR is `CONFLICTING`, `MERGE CONFLICT:` and the orange label (step 1.3), and merge neither PR. Only when both heads are unchanged and the PR is mergeable, go on to step 2.
- **Merge no other server PR** into `development` while a suite runs or waits: the suite tests your merge M on today's `development`, and a second server merge would mean the tested commit is not the one that lands. A second server card waits (leave it without comment; it is next once the first has merged or failed). A card with both a <app-repo> PR and a server PR moves as one, after its suite. A card that `DEPENDS ON:` the waiting card's PR waits (the skip rule above).
- **When the suite card merges, fails or goes red**, the others you merged are unaffected. Before your report, the suite card is finished (merged, or sent back with `CHECK FAILED:`); you never end with a suite still running unless the wait hit an error, which you report.

## Reverted culprits


When a 🚨 card's revert PR merges (its body names each culprit card and the merges of it that it reverts), after its `MERGED:`: on **each** culprit card the body names, one `REVERTED: <repo>#<n> @ <the revert commit, 40 characters>` per merge reverted, the note `(reverted by <owner/repo>#<revert PR>)` on that PR's line in the culprit's description, and that culprit card to the top of TODO (an `[AGENTS]` card: the top of WORKFLOW 🤖) (from wherever it is: MERGED, RELEASING, DONE). Its name keeps the reverted PR's number. Several culprits: each gets its own `REVERTED:` lines, notes and move.

## Test-host changes

A merge into development that changes `infra/test-host/` or the TestHostStack code starts a server workflow that deploys the test hosts. Find its run and wait on it with `ci-wait.sh run`; a failure goes in your report with the run's link; `RUN: STUCK …` (exit 6) goes in your report with the step it names, and you never rerun or cancel it.

## Never

- Run any test but UNIT on the merge and the API workflow, push your local merge commit anywhere but the temporary `merger/<pr>-<sha>` branch of step 5 (and delete that branch afterwards), deploy anything, or touch a test server or an emulator.
- Merge a PR the review policy does not pass, merge part of a card on purpose, squash, rebase or force-push, or push to any branch but the temporary one (never `main`, `development`, `staging` or a PR's).
- Merge an `[AGENTS]` card without a `VERIFIED:` naming each PR's current head (or with a newer `VERIFY FAILED:` for that head) unless the head is a carry candidate the merge gate accepts, or a card with the Blocked, orange or yellow label. Marking an unverified `CONFLICTING` `[AGENTS]` card (`MERGE CONFLICT:` and the orange label) is not merging it; do nothing else to it.
- Revert anything yourself: reverts are builders' PRs on a 🚨 card.
- Move a card into or out of QUESTIONS or REVIEW, except the review-policy send-back in step 1.

## Report (your final message)

The cards merged (name and link, each `<repo>#<n> @ <sha>`), the cards sent back and why (review, CI, a red check), the cards with `MERGE CONFLICT:` or `REFRESH NEEDED:` (for the board watcher's conflict fix or refresh), any temporary branch you could not delete, the cards merged green* with their flaky tests, the cards left in MERGING and why, any card you yielded or passed over (and for whom), the culprits marked `REVERTED:`, anything filed for flaky tests (cards and items), the cards merged during each server card's UNIT or suite wait (and, if a wait ended with a ready no-server-PR card unmerged, why), and any manual step for the user. Quote any denial verbatim.
