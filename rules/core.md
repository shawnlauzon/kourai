# board: shared rules

The rules are two files: this one, the core rules (`${CLAUDE_PLUGIN_ROOT}/rules/core.md`, shipped with kourai), and the project rules (`kourai-config get project.rules_file`: the **Project settings**, **Tests**, **Test servers** and **Releasing** parts, and anything the project adds). "rules.md" in an agent file or a rule means the two together. Every board agent reads the parts its own agent file lists (by section name: `[core: First to Last]` or `[project: Heading]` is read with one heading lookup and one Read, as each agent file says; `rules-ranges.sh check` keeps the names true), before the rest of its agent file; the board watcher, promoter, workflow builder and workflow verifier read both files whole. It holds what more than one role needs. Your agent file holds what only your role does. `.claude/board/WORKFLOW.md` is the overview. The user's decisions are one file each in `.claude/board/decisions/` (from 2026-10-18 on). Agents read them with Grep and Read (`.claude/board/decisions/*.md`, one small file each); `decisions-index.sh`, which prints them all in date order, is for the main session; `.claude/board/decisions-log.md` holds the earlier ones (closed history). When it, this file and the agent files disagree, that is drift: the workflow verifier reports it. The project's workflow Claude Doc is a kept-current description that follows the repo: where it disagrees with this file, the agent files or `WORKFLOW.md`, the repo wins, and the main session updates the doc after each workflow PR merges.

## The board

https://trello.com/b/<board-id>. Find list ids with `trelloReadList` action `list_by_board`. Find a list by its name word (lists carry emoji). If a list is missing, stop and report.

| List | Owner | What happens there |
|---|---|---|
| PROPOSED | **the user** | Ideas and proposals, from the user and from agents. The user approves a card by moving it to TODO (an `[AGENTS]` or docs card: to WORKFLOW 🤖), or archives it. Agents never take from it |
| BUG REPORTS | **the user** | The four standing cards on top ("Technical debt: High", "Technical debt: Medium", "Technical debt: Low", "Bugs: Low (edge cases)"), then non-urgent bugs (🪲) named by the bug and dependency upgrades (📦), from the user, the testers and agents that find them (Sentry triager, fraud watcher), filed by **Technical debt and bug cards** (a High flaky test too: `🪲 Flaky: …`). The user moves a card to TODO to have it fixed, or converts a standing card's item to a card. Agents never take from it, except the promoter's move of a card a release hold names, or the user names under "fix first", to the top of TODO, made 🚨 first (promoter.md, **Failed release**; the user's decision, 2026-10-27), and only once `user-setup-changes.md` section 45 is applied (`grep -c 'exception: the promoter renaming a 🪲 card' ~/.claude/settings.json` prints more than 0; until then the promoter waits as promoter.md says) |
| TODO | board watcher | Approved app, server and test work (never an `[AGENTS]` or docs card: those are in WORKFLOW 🤖). The board watcher takes a new card from the top into TESTING when a card test server is free (BEFORE); a returning card goes into BUILDING with no server. Worked in **List order** (below): 🚨 cards first, then returning cards, then the rest. **Nothing is done on a non-🚨 card here until it is picked up** (the user's decisions, 2026-10-18). Before pickup, nobody works on a non-🚨 TODO card, asks about it, labels it, moves it, archives it or sweeps it. A comment that records the card's own history or a finder's new evidence is not work. A card already picked up and waiting in TODO keeps its wait: its Blocked label, its `UNBLOCKED:` and its move to the top of TODO follow the Blocked-label rules (**Questions, manual steps and the Blocked label**). Four moves are not work on a TODO card: a stray `[AGENTS]` or docs card is moved to WORKFLOW 🤖 (board watcher step 2), the user's own comment on a card is routed with `ROUTED:`, the board watcher's `NOT VERIFIED:` comment and its move of a VERIFY card to the top of TODO, and a card in `NOT URGENT:` is renamed 🚨 and moved to the top (**Card titles and labels**); a `Release blocked:` card (first comment `RELEASE BLOCKER:`, no PR) already carries its wait, so its Blocked label (`board-wait.sh` owns it), the board watcher's `RESOLVED:` once its check passes and the move to DONE are not work either (**Releasing**). Its checks (a wait, a question, not agent work, an epic, a covered card) run when the board watcher takes it. A card with a title tag `[Webapp]`, `[REFERENCE]` or `[MILESTONE]` (not 🚨) stays here, untouched and never started; any other card no agent can work, 🚨 or not, goes to QUESTIONS at pickup (`From: TODO`) |
| WORKFLOW 🤖 | workflow builder, then workflow verifier (the board watcher moves cards in and out) | Every `[AGENTS]` and docs card, from the moment the user approves it until its PRs are `VERIFIED:`. The user approves by moving the card from PROPOSED here. The card stays here while its plan is written and agreed (`PLAN:` waits for the verifier's `PLAN AGREED:` or `PLAN CHANGES:`), and while it is built, verified and sent back (`VERIFY FAILED:`, `CHECK FAILED:`, `CHANGES REQUESTED:`, `REVERTED:` put it on top); on `VERIFIED:` naming every PR's head the board watcher runs the review policy and moves it to MERGING, or to REVIEW when the policy needs the user. It holds no test server and has no list limit of its own. A docs card is an `[AGENTS]` card whose PRs change only documentation (WORKFLOW.md, a README, a design doc), so it is named, checked and merged like any other `[AGENTS]` card. A mixed card (an app or server change plus a workflow part) is not named `[AGENTS]` and stays in the normal flow. Cards are started in **List order** (below) |
| QUESTIONS | **the user** | Decisions only: a question the user must answer. Never a manual step, never review. Exceptions: an answered card whose newest `CANNOT REPRODUCE:` is newer than its newest `BEFORE:`, `BEFORE FIXED:` or `REPRODUCED:` takes the CANNOT REPRODUCE paths instead (**A bug that cannot be reproduced**, After the answer): path 3b, its newest `BEFORE:`/`BEFORE FIXED:` starts with `BEFORE: skipped` and no `Not a no-UI card after all:` comment is newer than it, to the top of BUILDING with no server; path 3a, every other such card, `ANSWERED:` and a wait in QUESTIONS for a server and a new BEFORE run; and an answered card with no `BEFORE:` yet waits here for a card test server, or, when step 5's wait check stops it, Blocked with a `WAITS FOR:` (**Leaving QUESTIONS**) |
| BUILDING | card manager | The builders work on the card; **it holds no test server** (its builders may borrow a free one for a short check). A card waiting for a server for its AFTER run waits here with a `READY FOR TESTING:` comment. No `[AGENTS]` card is ever here |
| TESTING | card manager | A card holds a card test server **only while it is here**: its BEFORE run, its AFTER run, a test builder's step. One card per server. A card coming back for its AFTER run goes ahead of a new card for its BEFORE run, and 🚨 cards go first. While the release's full test runs a card still gets its server; its first emulator use waits (Settings: Release UI run) |
| REVIEW | **the user** | Cards whose PRs change what app users see. The user accepts by approving the PRs on GitHub |
| MERGING | merger | The merger merges each card as soon as it arrives, in the MERGING order of **List order** (below); a conflict fix, a refresh or a re-verify starts only for the top card |
| MERGED | promoter | Merged cards waiting for the next release |
| RELEASING | promoter, app builders | The cards of the one release in progress |
| VERIFY | **the testers** (the card's reporter; not the user) | Released cards created by someone other than the user or the Claude account wait here for the reporter's check (**VERIFY**, below). Agents never move a card out, except the board watcher's `NOT VERIFIED:` handling. The tester moves it to DONE when it works, or to TODO when it does not. No auto-move, no reminders |
| DONE | **the user** | Released cards, merged `[AGENTS]` and docs cards, resolved cards. The user archives them |

A card sits only in the list whose owner is acting on it. Agents never start work for a card in the user's lists (the one exception is the promoter's move of a release-hold card out of BUG REPORTS, in that row).

**Who starts whom.** The user runs `/run-board` (the main session). It starts the board watcher, and the workflow builder on `WORKFLOW WORK:`. The board watcher starts the card managers (one per card in BUILDING or TESTING, or in conflict-fix mode per conflicting or refreshing card in MERGING), the merger, the promoter, the app builders, the workflow verifier, the token auditor, the time optimizer, the fraud watcher and the Sentry triager (the promoter also starts it, in the foreground, for a release's Sentry resolve: promoter.md, **Sentry issues of the release**). A card manager starts its card's builders, the code reviewer and the feature tester. The main session talks to the user: it relays reports, posts answers as `USER REPLY:`, and interrupts the user for manual steps and sign-offs.

**List order** (the user's decision, 2026-10-18: "everything in the list should be handled top to bottom"). Every list is worked strictly top to bottom, and 🚨 means only a name that STARTS with 🚨.
- **The order of a list:** 🚨 cards in list position, then the rest in list position (what `board-snapshot.sh` prints). **MERGING** has one order for everything (the merger, the conflict-fix gate and the verifier check; `merge_order()` in `board-wait.py` builds it): 🚨 cards, then `[AGENTS]` and docs cards (a name that starts with `[AGENTS]`, 🪲 allowed in front), then the rest, each group in list position, and a card with `DEPENDS ON:` or `WITH:` after the cards it names. Putting list position ahead of the `[AGENTS]` tier would reverse the user's decision that ready `[AGENTS]` and docs cards merge right after ready 🚨 cards.
- **The top card** is the first card in that order that is eligible: not Blocked, not yellow, not person-owned, not carried (`INCLUDED IN:`), not a status card. An `[AGENTS]` card still waiting for `VERIFIED:` is eligible and can be top (the verifier starts for it). A card that waits on `DEPENDS ON:` or `WITH:` is never held back by the card it waits for. `board-wait.py` decides the top card from the cards' comments (`DEPENDS ON: <owner/repo>#<n>` names a PR, matched to the MERGING card whose description lists it; `WITH:` names the fixing card; `INCLUDED IN:` marks a carried card) and the board watcher names it in its start lines and prompts; no other agent works it out from `board-snapshot.sh`, which does not print those comments.
- **Outside MERGING** a lower card may start in parallel once every card above it has an agent on it. **Has an agent on it:** a builder, test builder, card manager, workflow builder or verifier was started for the card and is alive (`agent-state.sh` shows it). A card that only waits (for a server, a place) has no agent on it, so no lower card overtakes it, except in TODO: a returning card needs no server, so a new card above it that waits for a server never holds it back (**Test servers**). A higher card that is Blocked, carried, held or waiting on the user is skipped.
- **MERGING is a hard gate:** while an eligible card above has not merged, no conflict fix, refresh or re-verify starts for a lower card, only for the top card. Marking is not gated: the merger puts `MERGE CONFLICT:` and the orange label on every conflicting card, top or not. A lower orange card waits labelled; the next wake after a merge makes it top. Work already running finishes; only new starts are gated. The `Conflict fixes at once` setting is gone: a conflict fix holds no server, and the gate covers it.
- **Test servers:** a card waiting for its AFTER run is served 🚨 first, then in BUILDING order (top down), then by when it asked; a returning card goes before a new one. `kourai-project card-test-server.sh` reads the BUILDING order only to rank a BUILDING want; when it cannot read it, `waiting` and the `assign` of such a card exit 7 (never a guess by age) and the caller tries again on its next pass. Exit 3 keeps meaning "no server for this card now".
- **`NOT ITS TURN: <higher card name and link>`** is the report of a card manager or workflow builder started for a MERGING conflict fix or refresh whose prompt names a different top card than its own (it writes nothing and ends); **`NOT TOP: <card name and link> waits for <higher card name and link>`** is the main session's reply to the board watcher when it declines to start a workflow builder for such a card. Both are report lines, not card comments; the card comes back through the board watcher's top-card check.

**Person-owned cards.** A card with any member assigned is owned by a person. Agents never take, move or change it. The user owns every other card: never ask to assign one, and never assign members.

## A card's path

**App or server card:** PROPOSED → TODO → TESTING (its own branch; a card test server and emulator; FUNCTION BEFORE) → BUILDING (the builders; no test server; then the code review of every production-code PR) → TESTING (FUNCTION AFTER, a server again) → REVIEW if users see the change, else straight on → MERGING (merger checks and merges, server first, then mobile) → MERGED → RELEASING (full test, staging, app builds, SMOKE, uploads) → DONE, or VERIFY first when the card was created by someone other than the user or the Claude account (**VERIFY**, below). A card whose change no screen shows (the card manager decides at the start, from the card's description, and re-checks at AFTER) takes no BEFORE: the card manager comments `BEFORE: skipped, no UI change: <why>`, the card goes straight to BUILDING, and its AFTER run is its API tests and the smoke set, with no area UI selection, no new UI tests and no screenshots (a card never runs the whole UI suite; the full suite runs only in a release). A server change whose API behavior is new still gets its API tests red first. If a screen turns out to change, it is a UI card after all and takes BEFORE and AFTER as below. A failed AFTER run sends the card back to BUILDING and releases the server; it returns to TESTING for the next AFTER run ahead of new cards. A conflict or a refresh in MERGING is fixed without a test server and without leaving MERGING. A bug card whose reported symptom the BEFORE run (or the builder's first failing test) cannot reproduce goes to the user, not to the builders (**A bug that cannot be reproduced**).

**`[AGENTS]` and docs card:** PROPOSED → WORKFLOW 🤖 (the plan round first: the workflow builder posts `PLAN:` and the workflow verifier agrees with `PLAN AGREED:`, with no file, branch or PR until then (**Plan first**); then the workflow builder builds it and the workflow verifier checks each PR there; never TESTING, no test server, no test bucket) → MERGING → DONE. The card stays in WORKFLOW 🤖 until `VERIFIED:`; the merger takes it from MERGING. A PR that touches hooks, settings, `.github/` or a privileged helper goes to REVIEW (after `VERIFIED:`) before MERGING.

**Bug card:** BUG REPORTS → TODO (the user's move) → then as an app or server card.

**🚨 cards** filed by agents skip PROPOSED and BUG REPORTS and go straight to the top of TODO; a 🚨 `[AGENTS]` card goes to the top of WORKFLOW 🤖. **Every other card an agent creates goes to the bottom of its list** (a status card, which marks its list's stage, stays on top) (`pos: "bottom"`; the user's rule, 2026-10-19: "When you create new cards, put them on the back of the queue, not the front"): a QUESTIONS card, a proposal in PROPOSED. Only a move of an existing card goes to the top, as below. Every other non-urgent 🪲 bug and every 📦 dependency card an agent finds goes to the bottom of BUG REPORTS (the four standing cards stay on top there). Cards already filed on top stay. A code review's notes, and the findings of the other agents that are not their own 🪲 card, are filed by **Technical debt and bug cards** (**Card titles and labels**): a bug-named 🪲 card for a High or Medium real bug, otherwise an item on a standing card; agents never pick them up.

**Returning cards go to the top of TODO** (an `[AGENTS]` card: the top of WORKFLOW 🤖), put there by whoever moves them: changes requested (also a card dragged from REVIEW), `CHECK FAILED:`, `REVERTED:`, `VERIFY FAILED:`, a paused or unblocked card, a card a tester moved from VERIFY to TODO (`NOT VERIFIED:`; unlike the others it is a NEW card for pickup: its BEFORE run reproduces the tester's report, on a new branch, **VERIFY** below). **An answered question is not one of them** (the user's decision, 2026-10-22): an answered card with a `BEFORE:` comment goes to the top of BUILDING (a card manager, no server; but an answered card whose newest `CANNOT REPRODUCE:` is newer than its newest `BEFORE:`, `BEFORE FIXED:` or `REPRODUCED:` takes the CANNOT REPRODUCE paths instead (**A bug that cannot be reproduced**, After the answer): path 3b, its newest `BEFORE:`/`BEFORE FIXED:` starts with `BEFORE: skipped` and no `Not a no-UI card after all:` comment is newer than it, to the top of BUILDING with no server; path 3a, every other such card, `ANSWERED:` and a wait in QUESTIONS for a server and a new BEFORE run), one without waits in QUESTIONS for a server (**Leaving QUESTIONS**), an `[AGENTS]` card goes to the top of WORKFLOW 🤖. 🚨 cards go to the top of every list; every other new card to the bottom. "The top" is the move's position `top`.

**A card's PRs move as one.** All of a card's PRs (mobile, server, tests) are on the card itself. The merger merges none of them while any one conflicts or fails a check. If the server PR already merged and the mobile PR then fails, only the unmerged PRs are fixed and merged.

**PRs on the card.** Whoever opens a PR, in the same step:
- comments `PR: <url>`;
- adds `**PR:** <owner/repo>#<n>, <full link> (<one line on what it does>)` at the top of the description (read it first, keep the rest unchanged; newest PR line last);
- adds the number to the end of the card's name: `(#N)` for a mobile PR, `(server #M)` for a server PR, `(#N, server #M)` for both, mobile first.

A PR line is never deleted. A closed, replaced or reverted PR gets a note on its line: `(closed, replaced by #M)`, `(reverted by owner/repo#R)`, `(included in owner/repo#M)`. A closed or replaced PR leaves the name; a merged or reverted one stays. The board watcher fixes missing lines and wrong names.

## Card titles and labels

**🚨 at the start of a title** marks urgent work, and is the only thing that does (the user's decision, 2026-10-18: no "Urgent, prioritize me!" label): the fix for a failed release or a regression (something that worked before and broke), or a workflow change the user calls urgent (`🚨 [AGENTS] …`, the user's decision, 2026-10-17). Only the user's word makes a workflow change urgent: agents never mark one 🚨 for urgency on their own (a workflow script or gate that broke is a regression, as before). It goes first everywhere (the top of the next list), may take over a normal card's test server (an app or server card only: an `[AGENTS]` card uses none), ignores list limits, has the urgent fix deadline and, in MERGED, makes a release due by itself. **A work card that the release, or 2 or more other cards, wait on is 🚨 when it is filed**, by whoever files it (the user, 2026-10-19: "well obviously it should have had urgent added immediately"): a fix, a repair of staging, `main` or `development`, an environment repair, a release that cannot start. A pure decision stays a QUESTIONS card (never 🚨) and the work card, if any, is the 🚨 one. A manual step only the user can do stays a manual step, on a plain `Release blocked: <step>` card (**Releasing**), never 🚨. An `[AGENTS]` card is 🚨 only by the user's word, or as a regression; for any other, the filer proposes it in PROPOSED (**Releasing**). When such a card was filed or kept without 🚨, `board-wait.sh` prints `NOT URGENT:` and the board watcher renames the card (a leading 🪲 or 📦 is replaced by 🚨, any other name gets `🚨 ` in front), moves it to the top of its list and comments `URGENT ADDED: <what it holds, evidence>`; a user's removal of that 🚨 sticks (`board-wait.sh` stays silent for a card with an `URGENT ADDED:` comment, a card it saw lose its 🚨 and a card with a member). It marks work only, never a question or a manual step; say why in a comment. A fraud or money problem happening now is not a 🚨 card: it goes to the main session at once plus a QUESTIONS card.

**An `[AGENTS]` card** is a workflow card: its name starts with `[AGENTS]`, or with 🚨 or 🪲 and then `[AGENTS]` (`🚨 [AGENTS] …`). Every rule, script and gate that picks out `[AGENTS]` cards uses this test.

**🪲 at the start of a title** marks a bug that is not urgent, named by what the bug is (never by where it was found, never a `[BUG]` prefix), and a High flaky-test card (`🪲 Flaky: …`). It is filed in BUG REPORTS. Which findings get a card and which an item on a standing card is **Technical debt and bug cards** (below). A 🚨 card carries only the 🚨.

**📦 at the start of a title** marks a card whose fix is upgrading an outdated or vulnerable dependency (a gem, an npm/pnpm or pub package, a GitHub Action, a Docker base image): not a bug in our code, so never 🪲. It is filed in BUG REPORTS like a non-urgent 🪲 card (the user moves it to TODO), and a security advisory stays named in the title. A dependency problem that is urgent (a live exploit, a failed release) is 🚨 instead. Everything else treats a 📦 card as it treats a non-urgent 🪲 bug card, except the `[AGENTS]` name: 📦 never comes before `[AGENTS]`. A dependency upgrade in the workflow's own files (hooks, `.claude/bin`, `.github/`) is a plain `[AGENTS] …` card.

**Technical debt and bug cards** (the user's decisions, 2026-10-22: "What if we maintained a single card which had all of the Technical debt there, organized by approximate severity", "Real bug cards should be created one by one, named by what the bug is, not named by where it comes from", "a single low card for the edge cases. The medium card should be tracked individually", "a single card per severity ... mobile and server, separated"). This is where every agent files a non-urgent finding that is not a 🚨 card: a code review's notes, a tester's or builder's finding, a Sentry or fraud finding, a flaky test. 🧹 is no longer a title prefix and no agent files a 🧹 card. A bug the user wrote keeps the user's own card. A bug a tester (anyone but the user and the Claude account) wrote, folded into or replaced by a card an agent files, hands its reporter on: the new card carries `REPORTER: @<username>` (**VERIFY**).
- **Four standing cards**, always on top of BUG REPORTS, found by exact name (`trelloSearch`, then the BUG REPORTS list): "Technical debt: High", "Technical debt: Medium", "Technical debt: Low", "Bugs: Low (edge cases)". Each has checklists named exactly "Mobile" and "Server". The user converts an item to a card and moves it to TODO; agents never work from these cards and never edit their descriptions. A standing card that cannot be found by its exact name is created by the filer with `trelloWriteCard` `create` (its exact name, `pos: "top"`, one description line saying what it is), after one more search to see that no other filer just did; two cards of one name: use the first by position. A missing checklist is created by the filer (`trelloWriteChecklist` `create`, the exact name); when names repeat, use the first by position and never create a third.
- **Severity** (the code reviewer rates each note; any other filer rates its own finding; a card manager may raise a rating with a reason, never lower it): **High** = users or the business would hit it often, or it blocks the release or the board (for debt: a risk that makes the next change dangerous); **Medium** = would be hit now and then; **Low** = rare or cosmetic.
- **A real bug** names something a user or the business would hit: wrong behavior, a crash, lost data, money or security. **High or Medium:** its own 🪲 card at the bottom of BUG REPORTS, named by the bug in words ("A chat message sent while offline shows as sent"), never "Code review bugs from …". One card per problem, not per repo (a bug that needs the app and the server is one card; the card manager splits aspects as usual). Description: the scenario, where it was found (review or run link, reviewed card link), the aspects. **Low (an edge case: a rare race, a double tap, a wrong message):** an item on "Bugs: Low (edge cases)", in the checklist of the repo it lives in.
- **Everything else** (a cleanup, a duplicate, a redundant check, test debt, a note that is not a bug) is an item on the debt card of its severity, in the checklist of the repo the code lives in (a test lives in the repo of its tests).
- **An item** is one line, added with `trelloWriteChecklist` `add_item`, never by editing a description (two filers writing at once cannot overwrite each other): `<what is wrong, in words> (<owner/repo>#<n> review: <comment link>; card: <reviewed card name and full link>)`; for a flaky test the failing run's link and first failure line replace the review. A finding that needs a product decision (the review tags it `ask on this card`) is an item that starts `Question: <the question, options, your recommendation>` followed by the same parenthesis; on a High or Medium bug card the question goes in its description. Nobody asks the user at filing.
- **Before filing, one read:** `standing-card.sh "<standing card name>" --find <words from the finding> [--link <review or run url>]` (it prints the card's ARI, each checklist's ARI, name and item count with `FULL` at 190 or more, and only the items that hold every word or the link, each with its ARI, checked state and text cut at 300 characters; `MISSING card` or no `CHECKLIST` line of a name means it is absent). While `grep -c standing-card.sh ~/.claude/settings.json` prints 0, or the script exits 1, make the old full read instead: `trelloReadChecklist` `list_by_card` on the standing card (every checklist with its items). The read answers four things: the checklist exists; the same finding is already an item (then add the new evidence as a comment on the standing card quoting the item, and file nothing); an item already carries this review or run link (a restart: file only what is missing); the checklist is full. Also search BUG REPORTS and TODO (`trelloSearch`, words from the finding) for a bug card or `🪲 Flaky:` card on the same problem: comment the evidence there instead of filing. A checklist with 190 or more items (Trello holds 200) is full: use "Mobile 2" ("Server 2", then 3 …), created when absent. ## Related workflow changes: one PR

## Plan first

**Every workflow card starts with a plan, never with code (the user's decision, 2026-10-18, urgent):** "For all workflow items, the workflow builder should first write what they're going to do, and then the verifier verifies that that's correct. They go back and forth until they're in agreement. That should all be done before work is started to implement it." Several workflow PRs had failed verification after being fully built, mostly on design gaps a plan review would have caught, and each round cost a full rebuild.

- **The round.** The workflow builder posts `PLAN: revision <n>` on the card (what changes in each file and where; new phrases and who posts each; how the flow is driven and who starts whom; states and failure paths; cards already on the board; tests to add; any settings section or hook change; from revision 2 a "Disagrees with:" part for a verifier item it argues) and reports `PLAN READY: <card name and link>`. It writes no file and opens no branch or PR. The main session sends the board watcher `PLAN READY:` (like `WORKFLOW DONE:`), which starts the workflow verifier on the plan; `board-wait.sh` prints `VERIFY PLAN:` for a `PLAN:` that stayed unanswered for 10 minutes with no verifier alive on the card (the watcher starts the verifier on that too). The verifier posts `PLAN AGREED: revision <n>` or `PLAN CHANGES: revision <n>: <must-fixes>` (the bar of `VERIFY FAILED:`); a verdict makes the card workflow work again (`WORKFLOW WORK:`, why "plan agreed: build it" or "plan changes: revise"). They go back and forth until `PLAN AGREED:`. All state is on the card: the newest plan comment (`PLAN:`, `PLAN AGREED:`, `PLAN CHANGES:`) tells where the round stands, so any lost message is recovered from it.
- **Who needs a plan.** A card with a `PLAN:` comment is plan-first for good (a builder that hands off or dies mid-plan leaves a plan-first card for the next one). A card with no `PLAN:` comment and a `PR:` comment, a `HANDOFF:` or an origin branch `card/<shortLink>-*` was built before this rule and finishes under the old rule, its sent-back fixes (design changes included) too: no plan round and no plan check by the verifier. Every other card in WORKFLOW 🤖 is plan-first, a docs-only card too (a short plan).
- **Building.** Only after `PLAN AGREED:` as the newest plan comment does the builder implement, exactly the agreed plan. A step that departs from it (a file, state, rule or failure path not in the plan) stops the build: a new `PLAN:` revision, `PLAN READY:`, and a wait for a new `PLAN AGREED:`; a `PLAN:` newer than the last `PLAN AGREED:` voids the agreement, and while it is newer than the card's newest `AWAITING VERIFIED:` no final verifier starts for a head. The same applies to a send-back fix on a plan-first card that adds or changes a state, failure path or rule; a fix that only corrects code to the agreed plan needs no new round (the builder's report says "Design change: no, because <why>"). The PR body says "Plan: agreed at revision <n>; deviations: none or the agreed ones", and the final verification checks the PR against the newest agreed plan. That final verification is the **short pass** (the user's decision, 2026-10-18) for a PR whose card has an agreed plan, once settings section 36 is applied: the builder runs `workflow-checks.sh` first (the mechanical cross-file checks), and the verifier runs it again at the PR's 40-character head, checks the plan match, code-reviews the diff where it has a script or fixture (the `code-review` skill at medium, in its own detached worktree) and keeps the reads no script answers; the verdict phrases are unchanged. A card with no agreed plan, a PR that changes the checks themselves, or a lagging main checkout gets the full pass.
- **When the user is asked** (the user's decision, 2026-10-18: "rather than a number, to say if there's an actual disagreement, if it's not converging on a solution"). Plan rounds have no limit: they go on while each round closes the previous round's must-fixes. The builder posts `BLOCKED:` (both positions, options, a recommendation, `From: WORKFLOW 🤖`) in place of the next revision only when: (a) **a real disagreement:** the verifier keeps a must-fix the builder argued under "Disagrees with:" in the revision before, marking it `held: <item> (<why the argument does not change it>)`; or (b) **not converging:** the verifier's comment starts `PLAN CHANGES: revision <n>: not converging: <why>;`, which it writes only when a must-fix reopens one an earlier revision resolved, or when this round's must-fixes are no fewer or smaller than the round before's (small ones left out). Small, concrete must-fixes (exact wording, one test expectation, which PR to build on) never count toward either and never go to the user, even when held: the builder makes them. The user's answer is binding. A plan that needs a user decision is a `BLOCKED:` instead of a `PLAN:`. The 🚨 deadline counts an unanswered `PLAN:` as waiting for the verifier.

## The review policy

The user reviews only what app users see, plus what keeps the agents in check. One read-only script decides from each PR's changed files and its body, never from an agent's say-so: `kourai-hook review-policy.sh check <owner/repo>#<n>`. It prints one line: `NO REVIEW NEEDED:` or `APPROVED:` (exit 0, may merge), `REVIEW NEEDED:` (exit 1), `ERROR:` (exit 2: not known, check again later).

A PR's `App-visible: yes|no — <why>` line feeds it (the server and mobile builders write it, the card manager checks it). **One test for both repos (the user's decision, 2026-10-17):** `yes` only when an app user would see or experience something different (a screen, text or a message shown, a flow, a charge, a push or email, a status the app shows). `no` for a changed response the app never triggers or never shows, internal fields the app ignores, logging, and retries or caching under an unchanged UI. Worked `no`: <server-repo>#123 (an upload without a file now answers 422 instead of 500; the app always sends a file). A real doubt about whether users would see it: `yes`; never `no` to avoid a review. **Server:** any code outside `test/`, `tests/`, `docs/`, `.claude/` and Markdown needs review unless the line says `no` (routes, controllers, views, channels, mailers and locales no longer need review whatever the line says). **Mobile:** a change to `lib/` alone needs review unless the line says `no`. A missing or unreadable line counts as `yes`. `assets/`, `android/`, `ios/`, the other platform folders, `pubspec.*`, `fastlane/` and any new top-level file always need review whatever the line says (images and fonts users see, signing and permissions, dependencies, builds that go to outside testers). Hooks, settings, `.github/`, privileged-helper changes and the server's `infra/` always need review. (This works only once `user-setup-changes.md` section 25 is applied; until then the script sends every `lib/` change and every server controller, view, route, channel, mailer and locale change to review, and the agents go by its line.)

**An approval stays valid through a remerge, always (the user's decision, 2026-10-16):** every commit since it is a merge of the base, whatever the resolution changed, even a resolution that changed behavior. Only a commit that is not a merge of the base voids it, except a commit whose changed files are all under the repo's test and docs directories (mobile: `test/`, `integration_test/`, `docs/`; server: `test/`, `tests/`, `docs/`; a moved file counts by its old path too) (the feature tester's AFTER commits of tests): those keep it too. A behavior-changing remerge still gets its AFTER run and green CI, but never goes back to REVIEW for a fresh approval; the conflict resolution itself goes unreviewed (the user accepted that). (The script keeps the older rule, a `Behavior change:` note after the approval voids it, and so does a commit of tests, until the hook patch in `user-setup-changes.md` section 23 is applied; until then the script's line decides and a card it sends to REVIEW goes there.) ## A bug that cannot be reproduced

The user's decision, 2026-10-29 (card <card link>): "I don't want you to not be able to reproduce and then to fix some other issue that is not what the user saw!" and, on the wording: "the tester might report the error slightly differently, so don't be too pedantic on that. but it needs to reproduce the same issue". - **Which cards.** A card that reports a bug: a user's bug report (any name), a 🪲 card (code-review bug cards too), a `NOT VERIFIED:` card (the tester's report), a Sentry card (the Sentry error itself), and a 🚨 regression or failed-release fix card (its symptom is the failing test and assertion the card names). `🪲 Flaky:` cards, tests-only cards and feature cards are not bug reports: their BEFORE may pass or fail for the card's own reason and they write `Symptom: none, not a bug report: <why>`.
- **Reproduces.** The BEFORE test (or, on the skipped-BEFORE path, the builder's first failing unit test) fails because of the same broken behavior the card describes: the same screen, step or feature and the same wrong outcome. The wording, the message text or the exact value need not match. A failure for another reason (a different step, a setup or selector error, a different bug) does not count.

If the symptom shows only under such a condition, the bug is not reproduced: **Cannot reproduce** applies, and the side-condition behavior is reported as `different bug: <what, evidence>` (filed by the rule of **A different bug found on the way** only when it is a real defect), never as the cause. **Honest causes:** the word "cause" is written in a comment, report, `BLOCKED:` or PR only when the BEFORE test on the reporter's path proves it; otherwise "a possible cause" and what would confirm it. **A `setup:` miss** (an item of the `Symptom:` line's `setup:` part that is not `from the card`, `default` or `variation:`) is repaired by the one BEFORE fix run, whose prompt says `<setup item> is not from the card or a default`: it removes the side-condition tests from the card's branches (tests only), reruns on the ordinary path, then posts `BEFORE FIXED:` with a new `Symptom:` line or reports `blocked: cannot reproduce` (handled as **Cannot reproduce**), and reports the side-condition behavior as `different bug:`. Never a rerun until it fails, and never a test widened to something else. When the feature tester is unsure whether it reproduced, it did not.

## Liveness, pauses and waiting

**Liveness comes from transcripts.** Agents write no heartbeats. `agent-state.sh` reads each agent's transcript and running children (`running`, `waiting`, `unknown`, `handed-off`, `reported`, `dead`). An agent is confirmed dead only when its transcript and its children both say so (its last entry is an API error such as "Autocompact is thrashing", or it ended its turn with no report, no open tool call, no live child and no running background command and wrote nothing for 20 minutes; or a foreground tool call, other than to a child agent, Monitor, a question or plan approval, has been open more than 60 minutes and the transcript has been quiet for 15 minutes: never while it wrote recently, since queued parallel calls run one after another; or it was stopped: its own interrupt marker is its last write, with no tool call open and no running background command, and it is dead at once, while a write after the marker (a resume) keeps it alive and a stop of its parent alone still waits for the quiet time); a final report, a "completed" status or an "interim" hand-back while a child runs proves nothing, and an agent with a live child is never dead (`unknown`). A background command counts as running only while a process holds its output file open (or until its notice is queued). Only a stopped parent (an interrupt, `TaskStop`) takes its children with it; a parent that reported, handed off, hit an API error or was replaced by a newer watcher leaves them running, so never stop an agent to end it, least of all a handed-off board watcher. `handed-off` is an earlier board watcher whose report began `HANDOFF:`: not a second live watcher, and its children are not dead. The lock of the release server held by a dead promoter is released by the board watcher before it starts the replacement. Never start a second copy of an agent that may be alive: a merger or promoter that finds another live copy when it starts ends at once, touching nothing; a restarted card manager waits for its card's live agents instead of starting new ones. Agents pass no `CARD_HEARTBEAT=` prefix; the test scripts keep their own keep-alive files.

**One owner per card.** A card manager and a workflow builder run `agent-state.sh --token` once and then `agent-state.sh --owner <shortLink> <type> <token>` as their first command, again before each card move and before each step's agents start. The card's holder is the oldest copy of that type on the card that is alive and has not reported. `OWNER:` goes on. `STAND DOWN:` or `ERROR:`: start, move, post or release nothing more, wait for any agent already started, and report with the first line `STOOD DOWN: <the line>`. The board watcher then starts nothing for that card.

**A handed-off board watcher never acts again.** After its `HANDOFF:` report, each wake by a child's report only makes it send the main session `RELAY: <agent> on <card name and link> reported: <short report>` and end its turn. `board-wait.sh` prints `OLD WATCHER ACTED:` when it did more; nobody stops it.

**Pauses.** The board watcher pauses a card with `PAUSE: for <🚨 card>`, a pause file `<state_dir>/pause/<shortLink>` (written after the comment is posted, with a line in it) and a message to the card manager. An empty pause file is no pause: every reader ignores it, so a stray file nobody wrote with a comment stops nothing. Every wait script, the server test runner and the app build wrapper check that file and stop at once with `PAUSED`. The agents push what is committed and take down what they brought up; the card manager releases the test server, comments `PAUSED:` with where the work stands and moves the card to the top of TODO. A paused run is void. **A 🚨 card starts on the pass the board watcher sees it, on a free server first (the user's rule, 2026-10-18):** a pause is only for the case that no server is free. If a server frees before the paused card has been handed over, the 🚨 card takes the free one and the board watcher lifts the pause (`PAUSE LIFTED:`, pause file removed, message to the card manager): the paused card keeps its server and goes on.

**Waiting.**
- Every wait is one blocking script that ends on its own within the wait limit and prints a verdict line (plus the failing tests' excerpt on a failure); the full log stays in a file. Run each with the Bash tool's `timeout: 600000` (the default of 120 seconds would cut it off). A longer run is waited on in steps: on a still-going answer (`RUNNING`, `CI: RUNNING`, `RUN: RUNNING`, `UP: RUNNING`, `WATCH TIMEOUT`), call the same wait again at once, with nothing else (after `UP: RUNNING <test-server> <id>`, the same `up` with `--job <id>` added).
- A long command runs through `run-bg.sh` with `run_in_background`, alone in its call; its `run-wait.sh` goes in the next call, never the same one.
- **Every run has its own log folder.** The scratchpad is shared by every agent the same session started (the board watcher's card managers, feature testers and builders of every card), so a log folder there (`--logs` of `tool/ui_test_all.sh`, the folder of `run-bg.sh`) names the card and the run: `<scratchpad, absolute>/<shortLink>/<what>-<run>`, where `<run>` is the run's start time from `date -u +%Y%m%dT%H%M%SZ` (the merger, which has no card of its own per run, uses the PR and its head: `<scratchpad, absolute>/<what>-<n>-<head7>`, `<head7>` the head's first 7 characters). Never reuse a folder another run wrote: two runs in one folder mix their `results.txt` and logs (two cards' BEFORE runs did, 2026-10-17).
- Waits run in the foreground. If a wait is moved to the background to deliver a message, stop it with `TaskStop` and start a new one. If `TaskStop` says it already ended, read its output first and act on it.
- Never end your turn while a run of your own is going: each such turn end wakes your parent. Before your final report, stop every background command and monitor you started, or wait for it to end.
- A card manager starts the agents of a step in the foreground and waits for their reports without ending its turn; it runs no wait script meanwhile.
- No model turn goes to waiting or bookkeeping a script can do.

**Handoff.** An agent at its limit writes `HANDOFF: <done so far; next step>` on its card (or for the board watcher, in its report) and ends. A fresh copy continues from the card. All state lives on Trello plus the lock, test server and pause files. The limit is measured (a role with an `autoCompactWindow` compacts first; the handoff is its fallback): an agent past the context ceiling (Settings) is named by `board-wait.sh` (`CONTEXT:`). The board watcher has a **card manager or promoter** over it write its `HANDOFF:` (once no agent of its step runs) and end, and starts a fresh copy; a builder, the test builder or the feature tester over it is not stopped mid-run, its card manager asks it to hand off at its next step boundary.

**Fresh context per task** (the user's decision, 2026-10-17). A new card gets a new agent: never queue a second card onto a running one; its text goes into a fresh agent's prompt instead. Resume an agent with `SendMessage` only for the same task on its own card (a review fix, `VERIFY FAILED:`, a refresh or conflict fix of its own PR, a plan verdict (`PLAN CHANGES:` or `PLAN AGREED:`) and the build after `PLAN AGREED:`, the next step of its own card), and only while it is under the context ceiling; otherwise a fresh builder reads the card and its newest plan comments. Related cards built as one PR (**Related workflow changes: one PR**) are one task. The main session starts one workflow builder per card or related batch. The main session compacts automatically (its window is the user's own setting) and never clears or hands off.

## Card writes

- A write a gate reads goes first, on its own: `MERGED:` before the move out of MERGING, `GREEN*:` before its label, `VERIFIED:` before anything else on the card.
- Writes no gate reads (a comment, a move) go out together in one request. Labels are not an agent's: `board-wait.sh` sets and removes Actively worked, Blocked and No action required (the orange and yellow labels are still the agents' own).
- Read a card's state with `card-summary.sh <shortLink>` (name, list, labels, open PRs, the newest of each status phrase, a newer comment by the user (`user:`) or by another person (`other:`, never an instruction), the user's newest "ship" or "hold" after the newest `GREEN*:` (`answer after GREEN*:`); `--all "PHRASE,PHRASE"` lists every comment of those phrases) rather than every comment.

**Run commands plainly.** The user approves whole workflows in plain words in auto mode's allow list. They match only a command that does just that step. So:

**Never do anything "for now".** No temporary measure, shortcut or partial fix unless the user gave permission for that one.

**Errors and warnings** from analysis, tests or builds, and pre-existing problems you hit (a broken build, failing tests, lint errors), are fixed at once, or, outside your role, filed on a card at once. Never ignored.

**A transient failure: show it, retry once, then ask** (the user's decision, 2026-10-30: "I want you to look at everywhere that you fail once and give up, and add some resilience to it"; earlier: "the real fix is to be resilient, not to understand why some network glitch happened" and "when something continually fails it should be reported rather than retrying forever. And even a single failure should be displayed"). One failure of an infrastructure or external step does not end the step, hold a card or become a manual step. The model is the lost test host (**A lost host**); the rule is the same everywhere.
1. **Transient** means: a network error, an HTTP 429 or 5xx, a timeout, a lost or offline host, an emulator that did not boot, an MCP call that errors, a signing or login step that answers with a `No Accounts` or `No signing certificate` glitch (2026-10-30, the iOS build of `client-build/1.2.0+165`), a CI runner that vanished. Each agent file that retries a step names the strings that count; in a builder's file they are matched only in the lane's error lines (what fastlane prints at the failure after the last `Step:` header), and a non-transient marker in those lines (`Compilation failed`, a compiler `error:`, `Could not find a valid`, a missing key file) wins over any transient string.
2. **Show it at once.** The agent sends the main session (`SendMessage` to `main`) one line: `SHOW RETRY: <step> [<card name and link>]: <what failed, one line>; retrying once; nothing to do yet`. `run-board.md` shows it as one line, no action. An agent with no `SendMessage` (the feature tester) ends its run with `transient: <step>: <what failed>`; its parent (the card manager) posts the `RETRYING:` comment, sends the line, and starts it again once with `Retry once: <what failed>` in the prompt. `SHOW LOST HOST:` stays the host-loss form.
3. **Record it.** Before the retry the agent posts `RETRYING: <step>: <failure, one line>` on the card (a release step: on the release status card). A `RETRYING:` is open only while no `RETRIED:`, `WAITS FOR:`, `BLOCKED:`, `UNBLOCKED:` and no failure comment of that step (`… BUILD FAILED:`, `TEST FAILED:`) is newer than it. An agent restarted while one is open counts the retry as spent and does not retry again. A retry that passes ends with `RETRIED: <step>: passed on the retry`.
4. **Retry once**, only the failed step, after a pause of 10 to 30 seconds or on a fresh resource where that fits (a restarted emulator; `kourai-project test-server.sh up` once more after an exit 10, with no `down`, since the failed `up` already took back its own user; `down` then `up` only for a stack that came up healthy and later became unusable; neither guarantees a fresh host).
5. **A second failure of the same step** is not retried: it becomes what it is today, a manual step (`WAITS FOR: you: <step>. Tried: one retry at <time>. Check: …`) or the step's own failure path. Never a third try. One exception inside a helper: `gh-app-token.sh` makes at most 2 tries in one call (one retry after 2 seconds, on a network error, 429 or 5xx, never on 401, 403 or 404); an agent sees no retry, and no `SHOW RETRY:` is sent for it. The three PreToolUse gates (`merge-gate.sh`, `staging-gate.sh`, `merged-comment-gate.sh`) do the same for each Trello request they make (2 tries, 2 seconds between, on a 429, a 5xx or a network error; never on another 4xx), inside one 50-second deadline for the whole hook; when the tries or the deadline are spent they deny with `<gate>: TRANSIENT: <step> (<why>)` or `<gate>: TIMED OUT: <step> at <n>s`, and the merger or promoter then does the `SHOW RETRY:` and one retry of the whole command (merger.md, promoter.md).
6. **Never retried, reported at once as today:** a red test (**Tests**: a failing test is rerun exactly once; flakes get fixed), a code or compile error, a denial or hook refusal (except the gates' own `TIMED OUT:` and `TRANSIENT:` denies, item 5, retried once), a missing credential or secret, a 401, 403 or 404, an upload after the upload step has begun (a build number uploads once), a deploy (a deploy is never re-run), and any step whose failure left a half-done write (check its state first).
7. **A dead agent** (the `dead` row of `agent-state.sh`; a `reported` row, or an agent that ended with `HANDOFF:`, is no death) is started again once. Whoever starts it posts `RESTARTED: <agent> on <card>: died (<why, one line>) [id=<the dead agent's id>]` in the pass in which it starts it (and not otherwise), then sends `SHOW RETRY:`. A death is the **second in a row** only when the dead row's id differs from the id in the newest `RESTARTED:` of that agent type on the card and no comment other than `RESTARTED:`, `RETRYING:` or `RETRIED:` is newer than that `RESTARTED:`; a dead row whose id a `RESTARTED:` already names is the same death (a deferred start, the 4-starts-per-pass cap, the 10-minute `AGENT: dead` repeat): no comment, no question, only the start. Only the type's newest row counts. A second death in a row starts nothing: the starter posts `BLOCKED: <agent> died twice in a row on <card> (<the two reasons and times>). Options: start it once more (no change: straight on); look into the cause first. Recommendation: <one>` with `From: <list>` (**A question for the user**): a TODO, WORKFLOW 🤖, BUILDING, TESTING or REVIEW card goes to the top of QUESTIONS (a TESTING card gets `kourai-project card-test-server.sh release <shortLink>` first); a MERGING, MERGED or RELEASING card stays in place with `WAITS FOR: <that QUESTIONS card, name and link>`. A `USER REPLY:` or `UNBLOCKED:` is a newer comment, so the count starts again after the answer. Not counted: an agent that died on a usage limit (`RESUME:`), a watcher handoff.
   - **Who counts which agent.** The board watcher: the card manager (conflict-fix mode too), the workflow verifier, the two app builders and the promoter. The card manager: its own children (mobile-builder, server-builder, test-builder, feature-tester, code-reviewer), a second death in a row going to the child's `blocked:` path with the server released. The watcher posts `RESTARTED:` for the workflow builder and then sends `WORKFLOW WORK:`; on a second death in a row it posts the `BLOCKED:` (`From: WORKFLOW 🤖`) instead. A child that dies with no live card manager is answered by the orphan card-manager restart: no `RESTARTED:` for the child. The merger is not counted (it is board-wide; the watcher restarts it with `SHOW RETRY:` only).
   - **App builders** are counted on the release status card; only a newer comment of their own platform (`IOS ` or `ANDROID ` phrases), a `WAITS FOR:`, an `UNBLOCKED:` or a `PROMOTING:` resets the count. **The promoter** is counted on the release status card for every step: any status-card comment except `RESTARTED:`, `RETRYING:`, `RETRIED:` and the app builders' own comments resets the count (a `FULL SUITE VOID:` of a restarted promoter does, and the promoter's void count ignores `RESTARTED:`, so the full test keeps one path). When no status card exists the watcher creates `🚀 RELEASE: idle` before it starts the promoter, to hold the count; the `From:` of the question is `MERGED` before the first step. Only the promoter's newest `agent-state.sh` row counts: a dead row older than a later reported or live row is history.
   - **No promoter start while the release status card is Blocked** (release due, `AGENT: dead`, `STUCK:`, a next release step). Blocked here means the status card's newest `WAITS FOR:` has no `UNBLOCKED:` or `RESOLVED:` after it; the label alone does not decide it (it lags the comment). The watcher's own `UNBLOCKED:` lets the start happen in the same pass, and for a green* "ship" or "hold" the watcher posts the sign-off's `UNBLOCKED:` first and then starts the promoter. `board-wait.py` stops the 10-minute `AGENT: dead` repeat for the promoter while the status card carries the Blocked label.

**An unavailable MCP** (Trello, GitHub, Docs): "unavailable" means the same call failed twice, about 10 seconds apart (the first failure shown, **A transient failure**); only then stop and report. Don't work around it.

**A blocker that hits several cards** is handled for all of them at once.

**The workflow is written down.** Every PR that changes an agent, a rule, the board or the infrastructure updates `.claude/board/WORKFLOW.md` in the same PR.
